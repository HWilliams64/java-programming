**Arbiter** - The supplied program that coordinates the Ghost game and checks its rules. Your player chooses a letter; the arbiter announces whose turn it is and when the game ends. For example, the arbiter writes `TEAM1:TURN`, and TEAM1 responds with a letter message such as `TEAM1:T`. Keeping these responsibilities separate lets two independently written players follow the same rules. A player must not send its own replacement turn announcement or keep responding after `GAME_OVER`.

**Game protocol** - The agreed message format and sequence of actions that cooperating programs follow. Ghost players share text with the arbiter, so each program needs to know both what a message means and when it may send one. In `TEAM1:T`, the colon separates the team name from its chosen letter. Correct punctuation alone is not enough: sending that message on TEAM2's turn still violates the protocol. Use the supplied parser and project files to establish the exact required operations instead of inventing method names.

**Word fragment** - The letters accumulated so far in the game. A fragment must remain a prefix, meaning the beginning, of at least one dictionary word. With the small practice dictionary `THERE`, `THEIR`, and `THEORY`, the fragment `THE` still has possible continuations. After adding `R` and then `E`, it becomes `THERE`, a complete five-letter word. A prefix check and a completed-word check answer different questions: a fragment can match a dictionary word's beginning and also complete a losing word. The practice dictionary does not replace the arbiter's real dictionary.

**Legal move** - A response that follows the project's letter, message-format, and turn requirements. A player sends one permitted ASCII alphabetic letter, formatted for its own team, only when that team receives a new turn. For example, `TEAM1:T` has the illustrated response shape. Whether it is appropriate also depends on the current turn and fragment. A correctly formatted letter can still lose by completing a dictionary word with five or more characters or by producing an impossible prefix. Evaluate the game result as well as the message format.

**ASCII** - A character standard that includes ordinary English letters, digits, punctuation, and control characters. This project permits the alphabetic letters from that standard as moves; it does not permit every ASCII character. For example, `T` is an ASCII letter, while `7` is ASCII but is not a letter. A character can be alphabetic in another writing system without meeting this project's narrower rule. Keep the allowed character set separate from the parser's exact formatting and letter-case requirements.

**Runtime argument** - A text value supplied when a program starts. Java receives these values as strings in the `args` array of its `main` method. The arbiter supplies the shared-file path as one argument, which the player reads from `args[0]`. In `java -jar player.jar "game files/shared state.txt"`, the quotes keep the path with spaces together as one argument. They are terminal syntax, not part of the path received by Java. Check the argument count before reading an array element during a manual launch; a missing argument is different from a supplied path that does not exist.

**Runnable JAR** - A Java archive that packages compiled classes and identifies the class used to start the program. It lets someone launch a player with a command such as `java -jar player.jar`, followed by any required runtime arguments. Packaging makes the application easier to move and test outside its editor. A successful build does not prove the package contains everything needed: launch the exact JAR from a clean location with its required data. Source files alone are not a substitute for compiled classes, and external files are not automatically included merely because the program used them during development.

**Entry point** - The place execution begins when Java launches an application. For this project's ordinary Java application, a starting class supplies `public static void main(String[] args)`. A runnable JAR records that class as its main class so `java -jar` can find the starting method. For the guide's separate probe, `--main-class ArgumentProbe` names that class when creating the archive. Naming the class does not create the method or package a missing class; the archive and compiled program must agree. The class does not have to be named `Main`.

**Integration test** - A check that connected components work together through their actual shared rules. A dictionary test can show that a prefix is recognized, and a file test can show that text is written. Neither alone proves that a player reads a real turn, chooses a suitable letter, and responds correctly to the arbiter. An integration test exercises that connection and compares the observed messages and game behavior with an expected result. Test repeated observations, later new turns, and `GAME_OVER` as well as a normal turn. One passing game is evidence for that run, not proof that every possible fragment or timing condition works.
